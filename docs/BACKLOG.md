## 1. Extend the incident schema for known gaps

**Labels:** enhancement, schema, needs maintainer approval

**Rationale.** The README "Known limitations" lists four facts the incident record cannot hold:
encryption status, notice language, guardian recipients, and the outcome of an exemption
assessment. Teams currently record them outside the tool or not at all, and the drafts and
checklist cannot reflect them. Adding fields must not resolve an ambiguity: AMB-05 (no threshold),
AMB-15 (exemptions) and AMB-19 (guardians) stay open.

**Acceptance criteria.**
- [ ] `incident.schema.json` gains, with `schemaVersion` bumped to 2:
  - encryption status of the affected data (e.g. `encrypted` / `not_encrypted` / `unknown` / `null`);
  - notice language(s) (list of language names or codes, or `null`);
  - affected principals who are children or persons with disability, as counts, and whether
    intimation is planned to them, to parents/lawful guardians, or both (counts only; no names);
  - exemption-assessment outcome per claim (`not_assessed` / `assessed` with a free-text
    reference to the assessment, never a legal conclusion generated by the tool).
- [ ] Version 1 records still import, either via an explicit migration with a visible notice or by
  rejecting them with a clear message; the choice is documented.
- [ ] `src/core/types.ts`, the form specification in `src/ui/model.ts` and
  `tests/ui-model.test.ts` "covers every leaf of incident.schema.json" stay in step.
- [ ] Encryption status does not change the checklist outcome; if shown, it is shown with an
  AMB-05 interpretation. A recorded exemption assessment does not by itself change the outcome
  from `requires_legal_determination`.
- [ ] Tabletop examples are updated to schema v2 and still pass `tests/tabletop.test.ts`.
- [ ] No field can hold contact details or names; `tests/security.test.ts` and the README privacy
  statement still hold.

## 3. Add ESLint as a development dependency

**Labels:** chore, tooling, needs maintainer approval (new dev dependency)

**Rationale.** `npm run check` is the TypeScript compiler with strict options; it catches unused
code and some control-flow errors but no lint rules (e.g. `no-restricted-globals`,
`no-restricted-syntax` for `innerHTML`/`eval`, import hygiene). Some of the guards in
`tests/security.test.ts` are regex scans that a lint rule would express more reliably.

**Acceptance criteria.**
- [ ] ESLint (flat config) and `typescript-eslint` added as **devDependencies only**, with the
  reason recorded in the pull request; no runtime dependency added.
- [ ] Rules ban `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`,
  `new Function`, network and storage globals in `src/`, and DOM globals in `src/core` and
  `src/generators`.
- [ ] `npm run lint` runs ESLint; `npm run check` keeps running the strict compiler checks; CI runs
  both.
- [ ] The README "Scripts" table no longer says "not ESLint".
- [ ] `npm audit --audit-level=high` still passes.

## 4. ARIA and screen-reader audit of the intake page

**Labels:** accessibility

**Rationale.** Only two things are checked automatically: arrow-key navigation between draft tabs
and a label on every input. Live panels, the error list, tabs, and `<details>` disclosures have not
been tested with a screen reader, and no Lighthouse or WCAG review has been done
([VERIFICATION.md](VERIFICATION.md)).

**Acceptance criteria.**
- [ ] Lighthouse accessibility audit run on the served page; results and fixes recorded.
- [ ] Manual test with at least one screen reader (e.g. NVDA on Windows) and one mobile screen
  reader, covering: form entry, error list links, clock-basis selection, panel updates, draft tabs,
  copy/download/import/export status messages.
- [ ] Full keyboard-only walkthrough of the page recorded, with any traps or missing focus states
  fixed.
- [ ] Live regions do not announce the once-per-second timer updates.
- [ ] README accessibility statement updated to say exactly what was tested, and nothing more.

## 5. Document and design handling of AMB-19 and AMB-20 in the generators

**Labels:** documentation, generators, needs maintainer approval (rule interpretation)

**Rationale.** AMB-19 (Data Principal includes parents/lawful guardians, Act s.2(j)) and AMB-20
(Data Fiduciary "in conjunction with other persons", Act s.2(i)) are recorded in
`docs/requirements.md` §5 but are not yet surfaced by the core checks or listed in the drafts.
Before any code changes, the approach needs to be written down and agreed so that the tool flags
these questions without answering them.

**Acceptance criteria.**
- [ ] A design note in `docs/` describes, for each of AMB-19 and AMB-20: when it applies (which
  recorded facts trigger it), how it is surfaced (interpretation entry, draft AMB list, review
  checklist item), and what the tool will **not** do (no choice of recipient, no choice of which
  fiduciary intimates).
- [ ] The note is approved by the maintainer.
- [ ] Only then: `AmbiguityId` gains AMB-19 and AMB-20, `AMBIGUITY_SUMMARIES` gains their reasons,
  and the drafts list them when the trigger facts are recorded (depends on item 1 for guardian
  recipients).
- [ ] `tests/traceability.test.ts` and `tests/generators.test.ts` cover both IDs; tabletop
  scenarios 4 and 6 still pass.

## 6. Decide whether to deploy the intake page on GitHub Pages

**Labels:** decision, deployment, needs maintainer approval

**Rationale.** The page must be served over HTTP(S) and cannot be opened from `file://`. A hosted
copy would make it easier to try, but a `<meta>` CSP cannot set `frame-ancestors`, GitHub Pages
does not allow custom response headers, and a public URL invites real incident data into a page
the team does not control the hosting of.

**Acceptance criteria.**
- [ ] A short decision record in `docs/` weighs: convenience; inability to set CSP and
  `frame-ancestors` headers on Pages; clickjacking risk; whether users will treat a hosted copy as
  an official or "safe" place for real data; versioning and cache behaviour.
- [ ] Decision recorded as one of: no hosting; GitHub Pages with stated limits; another host that
  can send the CSP as an HTTP header.
- [ ] If deploying: a pinned-SHA workflow builds `dist/app/`, `npm run check:network` passes
  against the deployed build's files, and the README states the hosting limits.
- [ ] If not deploying: README says so and keeps the local `npm run preview` instructions.
